# 수동 확인 안내

CI(`.github/workflows/ci.yml`)가 Windows·macOS·Linux에서 빌드, 테스트, 앱 자동 확인(`scripts/check-app.sh`)을
돌린다. 여기에는 **사람이 화면을 봐야만 알 수 있는 것**만 적는다. 한 번에 다 하지 않아도 된다.
확인한 항목은 PR이나 이슈에 "Windows ✓ 3번" 식으로 남기면 `docs/MILESTONES.md`의 "실기 확인 필요"를 지운다.

## CI가 이미 확인하는 것 (다시 볼 필요 없음)
- 단일 인스턴스: 두 번째 `plx`가 상주 인스턴스로 넘어가고 바로 끝난다, 동시 실행해도 인스턴스는 하나(나머지는 넘기고
  종료 코드 0), 강제 종료 뒤 재시작
- 잘못된 인자와 저장소 밖의 파일은 터미널에 오류를 쓰고 종료 코드 2
- 상주 인스턴스가 처음 부른 셸의 작업 디렉터리를 쥐고 있지 않다(macOS·Linux)
- 한글·공백 경로 전달, 한글 경로 저장소 파일 blame(커밋된 줄 + 미커밋 줄)
- blame이 끝까지 와서 거터를 그린다, 같은 파일을 다시 열면 캐시에서 온다
- 파이프로(명령 치환) 처음 실행해도 스스로 분리하고 창을 띄울 준비가 되면 돌아온다(릴리스 빌드). 분리한 앱이 뜨지
  못하면 그 기록을 보이고 실패로 끝난다(Linux에서 화면 없이 실행해 확인)
- `plx show`로 연 커밋 상세가 파일 목록과 diff를 그린다(한글 경로)
- `plx log`로 연 파일 히스토리가 rename 앞(옛 이름) 구간까지 그린다(한글 경로), 다시 열면 캐시에서 온다
- `plx log -L`로 연 라인 히스토리가 rename 앞 커밋까지 그린다(한글 경로)
- 인자 없는 `plx`가 커밋 그래프 첫 화면을 그린다(한글 이름 브랜치를 merge한 저장소, 레인 2개)
- 저장소 밖에서 `plx <폴더>`가 그 저장소의 그래프를 그린다. macOS는 `open -a parallax.app <폴더>`(Dock 아이콘에 폴더를
  놓을 때와 같은 Apple 이벤트)도 떠 있는 앱에 그래프로 열린다. 연 저장소는 최근 저장소 목록에 최근 순으로 남는다
- 다른 터미널의 커밋이 열린 그래프에 2초 안에 반영되고(Linux 약 0.2초), 고친 파일이 열린 작업트리 blame에 반영된다
- 그래프의 순서·부모·레인 연결은 `git log --topo-order`와 대조하는 테스트가 있다(fixtures, 원격·얕은 클론, commit-graph 유무)
- 릴리스 빌드가 오픈 소스 라이선스 고지를 만들어 실행 파일에 넣는다(파일이 있는지까지. 창은 아래 1-12)
- 릴리스 빌드가 설치 파일(Windows NSIS 설치 프로그램과 설치 없이 쓰는 zip, macOS DMG, Linux deb)을 만든다. 설치
  프로그램으로 설치하는 과정과 아이콘은 사람이 본다(아래 1-13~16). macOS 앱 번들은 ad-hoc 서명을 하고 그대로 앱 확인을 돈다
- AI 출처: git-ai 1.7.6·1.3.4(옛 형식)가 노트를 쓴 저장소 20개(rename, cherry-pick, amend, merge, 한글 경로 등)에서 줄마다
  에이전트가 1.7.6의 `git-ai blame --json`과 같다(`fixtures/git-ai`). 화면 표시는 아래 13
- 지연 측정: 콜드 스타트, plx 호출 → 첫 페인트, blame 첫 줄 표시(처음·캐시), 커밋 상세, 파일 히스토리 첫 50개(처음·캐시),
  커밋 그래프 첫 화면.
  결과는 Actions 실행 화면의 Summary에 있다

## 0. 준비 (한 번)

### CI가 만든 빌드 받기 (빌드 도구가 없어도 된다)

CI는 PR과 main의 커밋마다 앱 자동 확인을 통과한 설치 파일을 올린다(14일 보관). 그 커밋의 CI 실행(PR의 Checks 탭 →
CI, 또는 저장소의 Actions → CI)을 열고 Summary 맨 아래 **Artifacts**에서 파일을 누르면 그 파일이 그대로 받아진다
(GitHub에 로그인해야 한다). 게시한 릴리스(Releases)의 파일도 같다.

- **Windows:** `parallax_<버전>_x64-portable.zip`을 풀고 `plx.exe`를 실행한다. 처음 실행할 때 SmartScreen이 막으면
  "추가 정보" → "실행". 첫 화면의 "터미널 명령 설치"를 누르면 그 폴더가 사용자 PATH에 들어가 새로 연 터미널에서
  `plx`를 쓸 수 있다(14-10, 직접 넣어도 된다. Git Bash: `export PATH="/c/Users/<나>/plx:$PATH"`).
  설치 프로그램(`…-setup.exe`)은 1-15로 확인한다
- **macOS (Apple Silicon):** `parallax_<버전>_aarch64.dmg`를 열어 `parallax.app`을 응용 프로그램 폴더로 끈다.
  공증하지 않은 앱이라 그대로 열면 "Apple은 'parallax'에 … 악성 코드가 없음을 확인할 수 없습니다"라며 열지 않는다.
  그 창을 "완료"로 닫고 한 시간 안에 시스템 설정 → 개인정보 보호 및 보안 → 보안의 "그래도 열기"(Open Anyway)를
  누르고 암호를 넣으면 열린다(이 과정이 1-16). 터미널에서 열기 전에 내려받은 파일 표시를 지워도 된다
  (`xattr -dr com.apple.quarantine /Applications/parallax.app`, 1-16을 볼 거면 하지 않는다).
  터미널 명령 `plx`는 앱 첫 화면의 "터미널 명령 설치"로 설치한다(14-9, `/usr/local/bin/plx`). 스크립트로도 된다
  (이 저장소가 있으면 `sh scripts/install-macos-shim.sh`, 릴리스에도 붙어 있다):
  ```sh
  curl -fsSLO https://raw.githubusercontent.com/gembitious/parallax/main/scripts/install-macos-shim.sh
  sh install-macos-shim.sh
  ```
  → `/usr/local/bin/plx`(쓸 수 없으면 `~/.local/bin/plx`에 설치하고 PATH 안내를 출력한다).
  `plx`가 같은 창으로 막히면 위의 `xattr`를 한 번 실행한다

### 직접 빌드

필요한 것: git, [Volta](https://volta.sh)(Node·npm 버전을 `package.json`에 맞춰 자동으로 쓴다), [rustup](https://rustup.rs)
(`rust-toolchain.toml`의 Rust를 자동으로 받는다). Windows는 Git for Windows와 Visual Studio Build Tools(C++)도 필요하다.

```sh
git clone https://github.com/gembitious/parallax && cd parallax
npm install
npm run tauri build -- --no-bundle     # Windows·Linux: target/release/plx(.exe)
npm run tauri build -- --bundles app   # macOS: target/release/bundle/macos/parallax.app
```

빌드가 끝나면 `plx`를 PATH에서 부를 수 있게 한다.

- **Windows (Git Bash):** `export PATH="$PWD/target/release:$PATH"` (또는 `target/release`를 시스템 PATH에 추가)
- **macOS:** `scripts/install-macos-shim.sh target/release/bundle/macos/parallax.app` → `/usr/local/bin/plx`
  (쓸 수 없으면 `~/.local/bin/plx`에 설치하고 PATH 안내를 출력한다). 앱의 "터미널 명령 설치"도 된다

### 확인

`plx --version` → `plx 0.1.0`

이후 단계는 **아무 git 저장소 안에서** 한다(이 저장소도 된다). 개발 빌드 수치를 보려면 `PLX_PERF=1`을 붙여
실행한다(`` ` `` 키로 성능 HUD를 켜고 끈다).

## 2. blame 화면 (M1)

| # | 할 일 | 기대 |
|---|---|---|
| 1 | 이력이 긴 파일: `plx <파일>:<줄>` | 내용이 먼저 뜨고 왼쪽 거터가 곧 채워진다. 그 줄이 가운데에 선택돼 있다 |
| 2 | 거터 보기 | 같은 커밋이 이어지는 묶음의 첫 줄에 요약·작성자·"3일 전" 같은 시간, 모든 줄 왼쪽에 색 막대(최근일수록 주황, 오래될수록 파랑) |
| 3 | 파일을 고치고(저장만, 커밋 안 함) 다시 `plx <파일>` | 바꾼 줄이 "커밋 안 됨"(초록 기울임, 점선 막대) |
| 4 | 거터에 마우스를 올린다 | 카드: 커밋 요약, 전체 메시지, 작성자·이메일, 날짜(커밋한 곳의 시간대), sha, 바뀐 파일 수 |
| 5 | `j`/`k` | 커서가 줄 단위로 움직이고, 커서 줄 거터에 그 줄의 커밋 요약이 보인다. 같은 커밋 줄의 거터가 옅게 칠해진다 |
| 6 | `y` | "복사했다: abcd1234" 알림, 다른 곳에 붙여 넣으면 sha 전체 |
| 7 | 거터 클릭 | 그 줄의 카드가 고정(파란 테두리), `Esc`로 닫힘 |
| 8 | `/` 후 단어 입력, `Enter`·`n`·`N` | 검색 결과로 이동 |
| 9 | `?` | 단축키 도움말 |
| 10 | OS를 다크 모드로 바꾼다 | 배경·글자·거터 색이 읽힌다 |
| 11 | 한글 경로·한글 내용 파일, EUC-KR 파일 | 글자가 깨지지 않는다. EUC-KR이면 머리줄에 `EUC-KR` 표시 |
| 12 | 머리줄의 파일 경로를 마우스로 누른 뒤, 또 `?` 버튼으로 도움말을 열고 `Esc`로 닫은 뒤 `j`/`k`·`Enter` | 코드를 다시 누르지 않아도 키가 먹는다(커서가 움직이고 `Enter`는 커밋 상세) |

## 3. 이력 거슬러 오르기 (M1)

| # | 할 일 | 기대 |
|---|---|---|
| 1 | 여러 번 고친 줄에서 `,` | 그 줄을 바꾸기 직전 리비전의 blame으로 간다(머리줄에 sha, `뒤로 q · 1`). 커서가 그 줄 근처 |
| 2 | `,`를 몇 번 더 | 계속 거슬러 오른다. 처음 생긴 커밋에서는 "처음 생긴 커밋" 알림 |
| 3 | `q`를 여러 번 | 한 단계씩 돌아오고, 돌아온 화면은 커서·스크롤이 그대로다. 맨 앞에서 `q`는 창을 숨긴다 |
| 4 | `<` / `>` | 파일을 바꾼 이전·다음 커밋 버전으로 간다. `<` 다음 `>`는 원래 화면으로 돌아온다 |
| 5 | 같은 파일을 다시 `plx` | 거터가 거의 즉시 찬다(캐시). HUD를 켰다면 `(캐시)` 기록 |
| 6 | **Windows:** `core.autocrlf=true`(Git for Windows 기본값)인 저장소에서 커밋하지 않고 고친 줄에 `,`, 바꾸지 않은 파일에서 `<` | `,`는 그 줄 근처로 간다(1번 줄로 가지 않는다). 바꾸지 않은 파일의 `<`는 HEAD가 아니라 그 앞 리비전이다 |
| 7 | 큰 저장소에서 `<`를 누르고 답이 오기 전에 `q` | 닫은 화면의 답으로 새 화면이 쌓이지 않는다 |

## 4. 커밋 상세 (M2)

| # | 할 일 | 기대 |
|---|---|---|
| 1 | blame에서 어떤 줄에 `Enter` | 그 줄 커밋의 상세: 요약·작성자·날짜·메시지, 바뀐 파일 목록(상태 글자, +/−), 지금 파일이 골라진 채 diff |
| 2 | `j`/`k` | 다른 파일의 diff로 바뀐다 |
| 3 | `u` | 분할 ↔ 통합 보기. 다음에 열 때도 고른 보기가 유지된다 |
| 4 | `n`/`N` | 다음·이전 바뀐 부분으로 스크롤 |
| 5 | `Enter` | 그 리비전의 파일 blame, 처음 바뀐 줄에 커서 |
| 6 | `plx show HEAD~3` | 터미널에서 바로 커밋 상세가 열린다 |
| 7 | rename이 있는 커밋 | 파일 목록에 `R`과 `← 원래 경로` |
| 8 | 실행 권한만 바꾼 커밋(`chmod +x` 뒤 커밋)의 그 파일 | diff 위에 "실행 권한을 켰다 (100644 → 100755)"와 "내용은 그대로다" |
| 9 | (Windows) 줄 끝만 LF → CRLF로 바꾼 커밋의 그 파일 | diff 위에 "줄 끝: LF → CRLF". 바뀐 줄은 없다 |
| 10 | 파일이 수백 개 넘게 바뀐 커밋(git/git이라면 `plx show 1f010d6bdf`, 919개 rename) | 목록이 바로 보이고 줄 수가 `…`에서 숫자로 채워진다. 머리줄 합계 끝의 `…`이 사라지면 다 셌다. 목록 스크롤이 매끄럽고 `j`를 누르고 있어도 diff가 따라온다 |
| 11 | 4MB가 넘는 파일을 바꾼 커밋의 그 파일 | "파일이 커서(… MB) 내용을 비교하지 않았다. 그래도 보기" → 누르면 diff가 열린다 |
| 12 | 커밋 상세에서 `f`, `Esc`, `:`, `Esc` 뒤 `↓`·`PageDown` | `f`는 파일 찾기, `:`는 명령 팔레트를 연다. 닫은 뒤 diff가 화살표·PageDown으로 움직인다 |
| 13 | 긴 파일의 몇 줄만 바꾼 커밋의 그 파일 | 바뀌지 않은 부분이 "바뀌지 않은 줄 N개" 막대로 접혀 있고, 누르면 펼쳐진다 |
| 14 | (Windows) `PLX_PERF=1`로 앱을 띄운 뒤 처음 연 커밋 상세 | HUD의 `커밋 …` 줄이 0.3초 안이다. GPU 없는 CI VM에서는 앱이 뜬 뒤 첫 diff만 0.3~0.9초였다(메인 스레드는 놀고 화면에 나오기를 기다렸다). 넘으면 그 줄을 보내 준다 |

## 5. 파일 히스토리 (M2)

이름을 바꾼 적이 있는 파일로 한다(이 저장소에는 아직 없다. 큰 저장소라면 git/git의 `Documentation/git-log.adoc`).

| # | 할 일 | 기대 |
|---|---|---|
| 1 | `plx log <파일>` | 커밋 목록이 바로 뜨고(상태 글자, sha, 요약, 작성자, "3일 전"), 머리줄에 `커밋 N개`. 맨 아래에 고른 커밋의 sha·작성자·날짜 |
| 2 | 이름을 바꾼 파일 | 이름을 바꾼 커밋에 `R`과 `← 옛 경로`, 그 아래 옛 이름 시절 커밋에는 옛 경로가 보인다. 머리줄에 `이름 바뀜 N번` |
| 3 | `j`/`k`, `PageDown`/`PageUp`, `Home`/`End`, 마우스 휠 | 목록이 끊김 없이 움직인다(커밋 수천 개여도). `PLX_PERF=1`이면 HUD의 `히스토리 … 스크롤` 줄 간격 p95가 16.7ms 이하(60fps) |
| 4 | `Enter` | 그 커밋의 상세가 **그 파일 diff만** 보인다. `a`로 모든 파일 ↔ 이 파일만 |
| 5 | 상세에서 `q` | 히스토리로 돌아오고 고른 줄·스크롤이 그대로다 |
| 6 | `b` / `,` | 그 리비전 / 바꾸기 전 리비전의 파일 blame. 지운 커밋의 `b`는 지우기 전 버전 |
| 7 | `/` 후 단어, `Enter`·`Shift+Enter`, `Esc` 뒤 `n`/`N` | 맞는 커밋이 노랗게 칠해지고 그리로 옮겨 간다 |
| 8 | blame 화면에서 `H` | 그 리비전부터의 파일 히스토리(작업트리 blame이면 HEAD부터) |
| 9 | 지운 파일: `plx log <지운 경로>` | 지운 커밋(`D`)부터 보인다 |
| 10 | 저장소 폴더에서 `plx log .` | `git log`와 같은 커밋들(빈 커밋, merge 포함) |
| 11 | 한글 IME로 `/` 검색 칸에 `수정`(두벌식)을 치고 조합 중에 `Enter` 한 번, 다시 조합 중에 `Esc` | `Enter`는 첫 일치로 가거나 조합만 끝낸다(두 번째 일치로 건너뛰지 않는다). 조합 중의 `Esc`는 칸을 닫지 않는다. 그래프의 `/`도 같다 |

## 6. 라인 히스토리 (M2)

| # | 할 일 | 기대 |
|---|---|---|
| 1 | blame에서 줄 하나에 `L` | 그 줄을 바꾼 커밋 목록. 머리줄에 `라인 히스토리`와 `N줄` |
| 2 | 목록에서 `j`/`k` | 아래 칸에 고른 커밋이 그 줄들을 어떻게 바꿨는지(빨강 뺀 줄, 초록 더한 줄, 옛·새 줄 번호) |
| 3 | blame에서 `J`를 몇 번 눌러 여러 줄을 고른 뒤 `L` | 그 범위의 라인 히스토리(머리줄 `a–b줄`) |
| 4 | 파일을 고친 채(커밋 안 함) 줄을 골라 `L` | HEAD 버전의 같은 줄로 옮겨 연다(커밋 안 한 새 줄이면 그 근처 줄) |
| 5 | `b` / `,` | 그 리비전 / 바꾸기 전 리비전의 blame이 그 줄 근처에서 열린다 |
| 6 | `plx log -L 10,20:<파일>` | 터미널에서 바로 연다 |
| 7 | 이름을 바꾼 파일의 줄 | 옛 이름 시절 커밋까지 이어지고 옛 경로가 보인다 |

## 7. 가속 설정 (M2)

Bloom 필터가 없는 저장소로 한다. 새로 클론한 큰 저장소가 좋다(`git clone https://github.com/git/git`, 몇 분).
새로 클론한 저장소에는 대개 commit-graph가 없다(`.git/objects/info/commit-graph` 파일이 없다).

| # | 할 일 | 기대 |
|---|---|---|
| 1 | `plx log <파일>` | 머리줄에 노란 `가속 설정` 버튼 |
| 2 | 버튼 클릭 | 설명과 실행할 명령이 보이는 확인 창. `Esc`·바깥 클릭은 취소(아무것도 실행하지 않는다) |
| 3 | `실행` | 버튼 자리에 `가속 설정 중… N%`, 끝나면 "가속 설정을 마쳤다" 알림과 `가속됨` |
| 4 | 같은 파일을 `plx log`로 다시(캐시를 피하려면 다른 파일) | 히스토리가 더 빨리 뜬다(HUD의 `git 50개째`가 준다) |
| 5 | `git status`, `git log -1` | 저장소 상태·HEAD는 그대로다 |
| 6 | 다른 큰 저장소에서 `실행` 직후 `G` | 그래프 머리줄에도 `가속 설정 중…`이 보이고 버튼은 없다. 끝나면 두 화면 모두 `가속됨` |
| 7 | 얕은 클론(`git clone --depth 1 …`)에서 `plx log <파일>` | 버튼 대신 `가속 불가`. 마우스를 올리면 까닭(얕은 클론), 팔레트의 `가속 설정`도 그 까닭을 알린다 |

## 8. 커밋 그래프 (M3)

브랜치와 merge가 있는 저장소로 한다(평소 쓰는 저장소, 또는 7의 git/git).

| # | 할 일 | 기대 |
|---|---|---|
| 1 | 저장소 안에서 인자 없이 `plx` | 그래프가 뜨고 HEAD 커밋 행이 골라져 있다(맨 위가 아니면 가운데로 스크롤). 머리줄에 저장소 이름과 브랜치 |
| 2 | 레인 보기 | 커밋 점과 선이 끊기지 않고 부모로 이어진다. merge 커밋은 속이 빈 점, HEAD 커밋은 고리가 있다. `git log --graph --oneline`과 순서가 같다 |
| 3 | 이름표 보기 | 현재 브랜치는 파란 바탕, 다른 브랜치는 파란 테두리, 원격 브랜치는 회색, 태그는 노란 테두리. 넷 이상이면 `+N` |
| 4 | `j`/`k`, `PageDown`, `End`로 끝까지, 마우스 휠로 빠르게 | 끊김 없이 스크롤되고(60fps 목표) 행이 비어 있다가 곧 채워진다(`…`가 잠깐 보일 수 있다). `PLX_PERF=1`이면 스크롤을 멈출 때마다 HUD에 `그래프 … 스크롤` 줄이 생긴다: 간격 p95(굵은 숫자)가 16.7ms 이하면 60fps다. 그 줄의 숫자를 함께 보내 주면 좋다(macOS·Linux는 레인을 CPU 캔버스로 그리므로 설명의 '캔버스 p95'도) |
| 5 | `Enter` → `q` | 커밋 상세가 열리고 `q`로 같은 행이 골라진 그래프로 돌아온다 |
| 6 | 머리줄의 `HEAD` / `브랜치` / `원격 포함`, `R` | 범위가 바뀌고 고른 커밋이 새 그래프에서도 골라져 있다. `브랜치`에서는 숨긴 원격 브랜치 수가 보인다 |
| 7 | blame·파일 히스토리·커밋 상세에서 `G` | 그 커밋(blame은 커서 줄의 커밋)이 골라진 그래프가 뜨고 `q`로 돌아간다 |
| 8 | 다크 모드로 바꾸기 | 레인 색이 어두운 배경에 맞게 바뀐다 |
| 9 | `PLX_PERF=1`로 큰 저장소(git/git)에서 `plx` | HUD의 `그래프 …` 줄이 150ms 이하(예산) |
| 10 | `/`에 커밋 메시지의 한 단어(한글 포함) → `Enter`, `n`, `N` | 맞는 커밋으로 차례로 가고 보이는 행 중 맞는 것이 노랗게 강조된다. 끝에서 처음으로 돈다 |
| 11 | `/`에 `path:` + 자주 바뀌는 파일(예: `path:Makefile`) → `Enter` | 검색 칸 옆에 `경로 일치 N개`, 그 경로를 바꾼 커밋이 모두 강조된다. `n`/`N`으로 오가고 `Esc`(목록에서)로 강조를 지운다 |
| 12 | 없는 말로 검색하고 바로 다른 말로 다시 검색 | 앞 검색은 멈추고 뒤 검색 결과만 보인다(큰 저장소에서 앞 검색이 오래 걸려도) |
| 13 | (macOS) `PLX_PERF=1`로 `plx <파일>`(blame)부터 띄운 뒤 `G`, `q`, 다시 `G` | HUD의 `그래프 …` 줄 두 개가 비슷하다. CI의 macOS VM에서는 앱이 뜬 뒤 처음 연 그래프만 '표시'가 0.9~3.1초였다가(GPU 캔버스를 처음 쓰는 준비) 레인을 CPU 캔버스로 그린 뒤 0.27~0.56초다. 처음 것이 0.3초 넘게 느리면 두 줄의 숫자를 보내 준다(설명의 '캔버스'가 크면 그리기 자체가, '레인 그림'이 '표시'보다 훨씬 앞이면 다 그린 뒤 화면에 나오기를 기다린 것이 늦다) |

## 9. 라이브 갱신 (M4)

parallax에 그래프나 blame을 띄워 둔 채 다른 터미널(또는 Claude Code)에서 작업한다.

| # | 할 일 | 기대 |
|---|---|---|
| 1 | 그래프를 맨 위에 둔 채 다른 터미널에서 `git commit` | 1초 안에 새 커밋이 맨 위에 생긴다. 화면이 깜빡이거나 비지 않는다 |
| 2 | 그래프를 아래로 스크롤해 커밋 하나를 고른 채 다시 커밋 | 고른 커밋이 화면의 같은 자리에 그대로 있다(행 번호만 밀린다) |
| 3 | `git worktree add ../wt -b 시험` 뒤 그 워크트리에서 커밋 | 원래 저장소의 그래프에 `시험` 브랜치와 커밋이 나타난다 |
| 4 | `plx <파일>`(작업트리 blame)을 띄운 채 편집기로 그 파일을 고쳐 저장 | 곧 다시 그려지고 고친 줄이 미커밋(초록)으로 보인다. 커서 줄은 그대로다 |
| 5 | 4의 파일을 커밋 | 미커밋 줄이 새 커밋으로 바뀐다 |
| 6 | `plx log <파일>`을 띄운 채 그 파일을 고쳐 커밋 | 히스토리 맨 위에 새 커밋이 생긴다 |
| 7 | `git status`, `git fetch`처럼 참조를 안 바꾸는 명령 | 화면이 다시 그려지지 않는다 |
| 8 | 다른 브랜치에만 있는 파일의 blame을 띄운 채 그 파일이 없는 브랜치로 체크아웃했다가 돌아오기 | 없는 동안은 오류가 보이고, 돌아오면 다시 blame이 그려진다 |
| 9 | 라인 히스토리(`L`)를 띄운 채 그 범위 위에 줄을 더해 커밋 | 다시 그려진 라인 히스토리가 같은 코드(옮겨진 줄 범위)를 따라간다 |
| 10 | 그래프 위에 커밋 상세를 띄운 채 커밋한 뒤 `q` | 그래프가 새 커밋을 보이고 고른 커밋이 화면의 같은 자리에 있다 |
| 11 | `plx <파일>`을 띄우고 `f`(또는 `/`)로 입력 칸을 연 채 다른 터미널·Claude Code가 그 파일을 고쳐 저장 | 입력 칸이 그대로 있고 친 글자가 이어진다(화면 키가 되지 않는다). 머리줄에 `바뀜`, 칸을 닫으면 다시 그려지고 `/`로 찾던 말은 `n`으로 이어 찾는다 |
| 12 | 파일을 고친 뒤 `git commit -am 시험 && plx log <그 파일>`(커밋 바로 뒤에 연다). 다시 고쳐 `git commit -am 시험2 && plx <그 파일>` | 화면이 한 번씩만 열린다(열자마자 한 번 더 다시 읽지 않는다). `PLX_PERF=1`이면 HUD에 `히스토리 …`·`blame …` 줄이 하나씩만 생긴다 |

## 10. 워크트리 (M4)

`git worktree add ../wt1 -b 시험1`처럼 링크된 워크트리를 하나 이상 만든 저장소로 한다.

| # | 할 일 | 기대 |
|---|---|---|
| 1 | 그래프에서 `W` | 주 작업트리(지금·주 작업트리 표시)와 링크된 워크트리가 브랜치·HEAD 요약·경로와 함께 보이고, 지금 것 다음 줄이 골라져 있다 |
| 2 | `j`/`k`로 골라 `Enter` | 그 워크트리의 그래프가 열리고 머리줄 이름·브랜치가 그 워크트리다. `q`로 돌아온다 |
| 3 | 그래프 이름표 보기 | 다른 워크트리가 체크아웃한 브랜치는 점선 테두리에 워크트리 이름이 붙는다 |
| 4 | blame(`plx <파일>`)에서 `W` → 다른 워크트리 | 그 워크트리의 같은 파일이 같은 줄로 열린다 |
| 5 | 워크트리 폴더를 지운 뒤 `W` | 그 워크트리는 `폴더 없음`으로 흐리게 보이고 열리지 않는다 |
| 6 | blame에서 `,`로 옛 리비전에 간 뒤 `W` → 다른 워크트리 | 같은 리비전의 blame이 열린다(머리줄에 같은 sha). "파일이 없다"가 뜨지 않는다 |
| 7 | 라인 히스토리(`L`)에서 `W` → 줄이 밀린 다른 워크트리 | 그 워크트리에서 같은 코드 줄 범위의 라인 히스토리가 열린다 |
| 8 | 다른 워크트리에서 `git switch --detach` 후 커밋하고 그래프 보기 | 그 커밋이 그래프에 있고 `HEAD`에 그 워크트리 이름이 붙는다 |
| 9 | 그래프를 띄운 채 다른 워크트리에서 `git switch 다른브랜치` | 곧 이름표의 워크트리 이름이 새 브랜치로 옮겨 간다 |


## 11. 파일 찾기 (Quick Open, M4)

아무 저장소에서 `plx`(그래프)나 `plx <파일>`(blame)을 띄운다. 한글 경로는 fixtures의 `encoding` 저장소가 편하다.

| # | 할 일 | 기대 |
|---|---|---|
| 1 | `f`(macOS는 ⌘P도, Windows·Linux는 Ctrl+P도) | 화면 위쪽에 입력 칸이 뜨고 최근 연 파일부터 목록이 보인다. Ctrl+P가 인쇄 창을 띄우지 않는다 |
| 2 | 파일 이름 일부를 친다(예: vscode에서 `editoroptions`) | 글자마다 바로 바뀌고 이름이 맞는 파일(`editorOptions.ts`)이 맨 위, 맞은 글자가 파란 굵은 글씨다 |
| 3 | 한글 IME로 `파일`을 친다(두벌식: `ㅍ`·`파`·`팡`·`파이`·`파일` 순으로 보인다) | 치는 동안 결과가 비지 않고 `파일 이름.txt`가 계속 보인다. 조합 중에 `Enter`는 조합만 끝낸다 |
| 4 | 초성 `ㅍㅇ` | `파일 이름.txt`가 맨 위 |
| 5 | `설명:2` → `Enter` | `문서/설명.md` blame이 열리고 2번째 줄이 골라져 있다. `q`로 돌아온다 |
| 6 | 파일을 골라 `Shift+Enter` | 그 파일의 히스토리가 열린다 |
| 7 | `↑`/`↓`, Ctrl+N/Ctrl+K, PageDown, 마우스 | 고른 줄이 움직이고 목록이 따라 스크롤된다. 클릭하면 연다 |
| 8 | `Esc`, 바깥 클릭 | 닫히고 아래 화면의 키(`j`/`k` 등)가 그대로 먹는다 |
| 9 | 다른 터미널에서 새 파일을 `git add`한 뒤 다시 찾기 | 새 파일이 보인다 |
| 10 | `PLX_PERF=1`로 큰 저장소에서 빠르게 치기 | HUD의 `파일 찾기 …` 줄이 50ms 이하(예산) |
| 11 | 추적 파일 하나를 탐색기·Finder에서 지운 뒤(커밋하지 않고) 찾기 → `Enter` | 이름에 줄이 그어지고 "지움" 표시가 붙는다. `Enter`는 HEAD 버전 blame(머리줄에 sha)을 연다 |

## 12. 명령 팔레트와 에디터로 열기 (M4)

VS Code(`code`)나 Zed(`zed`)가 PATH에 있는 상태에서 한다. 없으면 터미널에서 `PLX_EDITOR`를 정한 뒤 `plx`를 다시
부른다(상주 앱을 끌 필요는 없다: 마지막 `plx` 호출의 셸 값을 쓴다).

| # | 할 일 | 기대 |
|---|---|---|
| 1 | 아무 화면에서 `:`(Windows·Linux는 Ctrl+Shift+P, macOS는 ⌘⇧P도) | 그 화면의 할 일 목록이 단축키와 함께 뜬다. Ctrl+Shift+P가 다른 창을 띄우지 않는다 |
| 2 | `ㅍㅎ`(초성) → `Enter` | `파일 히스토리`가 골라지고 실행된다(blame에서) |
| 3 | 그래프에서 팔레트 → `범위: HEAD` | 머리줄 범위가 HEAD로 바뀐다(마우스 없이) |
| 4 | 가속되지 않은 저장소의 히스토리에서 팔레트 → `가속 설정` | 확인 창이 뜨고 `Enter` 실행, `Esc` 취소 |
| 5 | blame에서 줄을 고르고 `o` | 에디터가 앞으로 오고 그 파일의 같은 줄이 열린다. 화면 아래에 `VS Code에서 열었다: 경로:줄` |
| 6 | `<`로 예전 리비전 blame에 가서 `o` | 작업트리 파일에서 그 줄에 해당하는 줄이 열린다 |
| 7 | 이름을 바꾼 파일의 옛 리비전(파일 히스토리의 아래쪽)에서 `b` → `o` | 작업트리의 새 이름 파일이 열린다 |
| 8 | 그래프에서 `o` | 에디터가 작업트리 폴더를 연다 |
| 9 | blame에서 `i`, 다시 `i` | 커서 줄의 커밋 카드가 고정돼 보이고, 다시 누르면 닫힌다 |
| 10 | Windows: 에디터를 띄울 때 | 검은 콘솔 창이 깜빡이지 않는다 |
| 11 | macOS: 앱을 Finder(또는 Dock)에서 띄운 뒤 터미널에서 `plx <파일>` → `o` | 터미널의 PATH에 있는 `code`·`zed`로 열린다 |

## 13. AI 출처 (M5, git-ai를 쓰는 저장소)

[git-ai](https://github.com/git-ai-project/git-ai)로 에이전트 작업을 커밋한 저장소에서 한다(`git notes --ref=ai list`에 무언가 나와야 한다).

| # | 할 일 | 기대 |
|---|---|---|
| 1 | AI가 고친 파일을 `plx <파일>` | 머리줄에 `✦ AI n줄`, AI가 쓴 줄 거터에 보라 줄과 `✦ claude` 같은 도구 이름 |
| 2 | 같은 파일을 `git-ai blame <파일>` | 1에서 보라 줄인 줄과 git-ai가 AI 도구 이름을 붙인 줄이 같다 |
| 3 | 보라 줄에서 `i` | 카드에 `AI ✦ 도구 · 모델`, 시킨 사람 |
| 4 | git-ai 노트가 없는 저장소 | 아무 표시가 없고 blame이 그대로 빠르다 |

## 14. 앱으로 열기와 터미널 명령 (M6-1)

터미널 없이 한다. 확인할 저장소 두세 개(이 저장소도 된다)를 준비한다.

| # | 할 일 | 기대 |
|---|---|---|
| 1 | 앱을 끝낸 뒤 Finder·Dock(macOS)·시작 메뉴(Windows)로 띄운다 | 첫 화면에 "저장소 열기… ⌘O"(Windows Ctrl+O), 최근 저장소, "터미널에서 열기"가 보인다 |
| 2 | "저장소 열기…"(또는 ⌘O·Ctrl+O) → 저장소 폴더를 고른다 | OS 폴더 창이 parallax 창에 붙어 뜨고, 고르면 그 저장소의 그래프가 열린다. 저장소 안의 하위 폴더를 골라도 된다 |
| 3 | 2에서 저장소가 아닌 폴더를 고른다, 폴더 창을 취소한다 | 저장소가 아니면 화면 아래에 까닭이 빨갛게 뜨고 보던 화면은 그대로다. 취소하면 아무 일도 없다 |
| 4 | 2를 저장소 몇 개에 한 뒤 앱을 끝내고 다시 띄운다 | 최근 저장소에 최근 순으로 보인다. 마우스로 누르거나 `↑`/`↓`(`j`/`k`)·`Enter`로 연다. ⌘O·Ctrl+O의 폴더 창은 가장 최근 저장소의 상위 폴더에서 시작한다 |
| 5 | 최근 저장소 하나의 폴더 이름을 바꾸고(또는 외장 디스크를 꺼내고) 창으로 돌아온다 | 그 줄이 흐리게 "없음"으로 보이고 눌러도 열리지 않는다. 줄 끝 ✕나 `Delete`로 목록에서 빠진다(폴더는 그대로) |
| 6 | Finder·탐색기에서 저장소 폴더를 창에 끌어 놓는다. 저장소 안의 파일도 끌어 놓는다 | 끄는 동안 "놓으면 연다" 안내가 창을 덮는다. 폴더는 그 저장소의 그래프, 파일은 그 파일의 blame이 열린다 |
| 7 | macOS: 저장소 폴더를 Dock의 parallax 아이콘에 놓는다(앱이 떠 있을 때와 끈 뒤 둘 다) | Dock 아이콘이 받아들이고 그 저장소의 그래프가 열린다. Finder에서 폴더를 더블클릭하면 그대로 Finder가 연다 |
| 8 | 아무 화면에서 `:` → `저장소`, 트레이(메뉴 막대) → 저장소 열기…(창을 닫아 둔 채로) | 팔레트에 "저장소 열기…"와 최근 저장소가 뜨고 고르면 열린다. 트레이에서는 창이 보이고 폴더 창이 뜬다 |
| 9 | macOS: 응용 프로그램 폴더의 앱 첫 화면에서 "터미널 명령 설치" | `/usr/local/bin`에 쓸 수 없으면(새 Apple Silicon 맥) macOS 관리자 암호 창이 뜬다. 넣으면 "터미널 명령 plx를 쓸 수 있다: /usr/local/bin/plx", 첫 화면은 "설치됨". 새 터미널의 저장소에서 `plx`가 이 창에 연다. 암호 창을 취소하면 까닭이 뜨고 아무것도 바뀌지 않는다 |
| 10 | Windows: 첫 화면에서 "터미널 명령 설치"(설치 프로그램으로 설치한 앱, zip의 `plx.exe` 둘 다) | 관리자 권한을 묻지 않는다. 새로 연 터미널(PowerShell·Git Bash)에서 `plx --version`이 된다. 설정 → "환경 변수"의 사용자 Path에서 다른 항목은 그대로이고 그 폴더가 끝에 붙는다(먼저 잡히는 다른 `plx`가 있으면 그 앞, 11). 다시 띄운 첫 화면은 "설치됨" |
| 11 | 설치한 뒤 앱을 다른 폴더로 옮겨 다시 띄운다. Windows는 zip을 다른 폴더에 한 번 더 풀고 트레이에서 앱을 종료한 뒤 새 폴더의 `plx.exe`를 띄운다(옛 자리는 남긴 채) | 첫 화면에 다시 설치 단추가 보이고, 누르면 `plx`가 새 자리의 앱을 부른다. Windows는 단추 옆에 "사용자 PATH의 <옛 폴더> 앞에 넣는다"와 "지금 plx 명령은 <옛 폴더>의 plx를 부른다"가 보이고, 누른 뒤 새 터미널의 `plx`가 새 자리의 앱을 부른다 |
| 12 | macOS: DMG를 연 채 그 안의 앱을 바로 띄운 첫 화면 | 설치 단추 대신 "디스크 이미지(DMG)에서 실행하고 있다…" 또는 "임시 자리에서 실행하고 있다…"가 보인다 |
| 13 | Windows: 앱이 떠 있을 때 시작 메뉴의 parallax를 다시 누른다 | 창이 앞으로 오고 보던 화면이 그대로다 |

## 15. 에디터 화면 (M6-2)

저장소 하나를 앱에서 연다(14의 2). Mod는 macOS ⌘, Windows Ctrl이다.

| # | 할 일 | 기대 |
|---|---|---|
| 1 | 저장소를 연다 | 왼쪽에 저장소 이름과 파일 트리(폴더 먼저, 추적 파일만), 아래 패널에 그래프, 맨 아래 상태 막대에 브랜치(`⎇ main`)가 보인다 |
| 2 | 트리에서 폴더를 눌러 펼치고 파일을 한 번 누른다. 다른 파일을 한 번 누른다 | 처음 파일이 이름이 기울어진 미리보기 탭으로 열리고, 다른 파일은 그 탭 자리에 열린다. 파일을 두 번 누르거나 탭을 두 번 누르면 기울임이 풀린 탭으로 남는다 |
| 3 | 탭 몇 개를 연 뒤 Ctrl+Tab·Ctrl+Shift+Tab, 탭의 ×, 탭을 가운데 단추로 누르기, Windows Ctrl+W | 탭을 오가고, 닫으면 그 앞에 본 탭이 보인다. 보이는 탭의 파일이 트리에서 펼쳐져 골라져 있다 |
| 4 | 마우스나 `j`/`k`로 커서를 옮긴다 | 커서 줄 끝에 흐린 글씨로 작성자 · 상대 시간 · 요약이 붙는다. 마우스를 올리면 커밋 카드, 누르면 카드 고정. 커밋하지 않은 줄은 초록 "커밋 안 됨" |
| 5 | `b`, 머리줄의 "blame 거터", 상태 막대의 "blame 거터 끔" | 줄마다 blame 거터가 보였다 숨는다(열린 탭 모두). 앱을 다시 띄워도 마지막 설정이 남는다 |
| 6 | Ctrl+G(macOS도 Ctrl), 상태 막대의 "줄 n, 열 m" | 줄 이동 칸이 뜨고 줄 번호를 넣으면 그 줄로 간다. 상태 막대의 줄·열이 커서를 따라가고, UTF-8이 아닌 파일은 인코딩, CRLF 파일은 CRLF가 보인다 |
| 7 | 탭에서 `H`, `L`, `Enter`, `G` | 아래 패널에 히스토리·라인 히스토리·커밋 상세·그래프가 열리고 머리줄에 지나온 화면이 `›`로 이어진다. 머리줄의 앞 화면을 누르면 그 화면으로 돌아간다 |
| 8 | 패널의 히스토리에서 `b`, 커밋 상세에서 `Enter` | 그 리비전의 파일이 미리보기 탭(이름 옆에 sha)으로 열린다. 그 탭에서 `q`면 탭이 닫히고 패널로 돌아간다 |
| 9 | 패널 머리줄의 ▴·▾·×, 트리와 패널의 경계선 끌기 | ▴는 패널이 가운데를 다 쓰고 ▾로 돌아온다. ×는 패널을 닫는다(Mod+J로 다시 연다). 끈 너비·높이는 다시 띄워도 남는다 |
| 10 | Mod+B, Mod+J, Mod+Shift+E(한글 입력 상태에서도) → 트리에서 `j`/`k`·`→`/`←`·`Enter`·`Space`·`Esc` | 트리가 숨었다 보이고 패널이 닫혔다 열린다. Mod+Shift+E 뒤에는 키로 트리를 고르고 `Enter`는 탭, `Space`는 미리보기, `Esc`는 에디터로 돌아간다 |
| 11 | 탭을 모두 닫는다 | 가운데에 파일 찾기·커밋 그래프·파일 트리·명령 팔레트·다른 저장소 열기와 그 키가 보이고, 누르면 그대로 된다 |
| 12 | 다른 터미널에서 새 파일을 `git add`하고 커밋한 뒤 창으로 돌아온다. 브랜치를 바꾼다 | 트리에 새 파일이 보이고 상태 막대의 브랜치가 바뀐다. 열린 그래프·작업트리 blame도 바뀐다(9번 라이브 갱신과 같다) |
| 13 | 터미널에서 `plx <연 파일>:<줄>`, `plx log <파일>`, 다른 저장소에서 `plx` | 같은 파일의 탭이 그 줄로 다시 열린다(탭이 늘지 않는다). 히스토리는 패널에 열린다. 다른 저장소는 그 저장소의 작업 공간으로 바뀐다 |

## 문제를 알릴 때
- 플랫폼(Windows/macOS 버전), 위 표의 번호, 실제로 본 것
- 가능하면 `PLX_PERF=1`로 실행한 성능 HUD 캡처
- 콘솔 출력이 필요하면 트레이에서 종료한 뒤 `PLX_DETACH=0 plx <파일>`로 실행한다(상주 인스턴스가 터미널에 붙어 로그가 남는다)
